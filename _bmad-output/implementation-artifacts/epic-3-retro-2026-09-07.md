O novo domínio `boarding/` seguiu o template estabilizado no Épico 2.

**AV2 — Mapa de duplicação (cresceu no épico; maioria já deferida).**
- `toInfraError` copiado para o 3º e 4º adapters — a task da própria 3.5a prescreveu copiar (`deferred-work.md`, seção 3-5a).
- `@Req() req: Request & { user }` (resolve para Request do DOM) copiado de `boarding.controller.ts` → `trip.controller.ts` (defer 3-5a).
- `['trip', id, 'students']` repetido como literal em 3 arquivos (defer 3-4b/3-5b).
- `ManagedRuntime` + event dispatcher best-effort: 3ª cópia (trip, boarding, routing) (defer 3-3a).
- **Nova (esta retro):** `trip.tsx` usa `isLoading` + retry default na query do roster enquanto `scan.tsx`/`student-list.tsx` usam `status`/`isPending` + retry custom — mesma entrada de cache com comportamento divergente entre telas (`trip.tsx:161,187,262` vs `student-list.tsx:30,58`).

**AV3 — God-class: `scan.tsx` (752 linhas).** Um único componente `ScanScreen` (5 `useState`; câmera + submit + interação com fila + feedback + hook E2E), cresceu através de 3.3b → 3.4b → 3.5b → 3.6 sem nunca ser fatiado. `trip.tsx` (491) é candidato borderline.

**AV4 — Reconciliação spec ↔ implementação:**
1. **AC #4 da 3.5b vale só online** — "um check-in feito na scan reflete na lista sem recarregar" não se sustenta no caminho offline (ver DS1). Desvio de spec a reconciliar ou corrigir.
2. **PLACEHOLDER_ROUTE_ID viveu o épico quase todo** — a tela do motorista não iniciava viagem pela UI; 3.1 ficou em review de abril a setembro; resolvido só em 06/09 por `spec-3-1-rota-real-do-motorista.md`. O smoke da 3.6 (06/09) precisou criar viagem via API por causa disso.
3. **Janela `occurredAt` (24h, `check-in.use-case.ts` MAX_OCCURRED_AT_AGE_MS) vs fila sem TTL** — a fila promete persistir (NFR11), mas o servidor rejeita `occurredAt` > 24h: trecho offline > 1 dia = embarque "salvo" que nunca será aceito (constava no defer 3-4b; realinhar as pontas é decisão de produto).
4. **ACs da 3.2b sem evidência de runtime** (Tasks 9.3/9.4 marcadas sem execução — defer 3-2b); fechado depois via 1.8 + smoke da 3.6. Lição: checkbox de verificação marcada sem execução passou pela story.

6. **F5-offline (Tier 1 persist) não verificável no alvo web dev** — deferido para device/Story 1.7 (aceito, limitação de ambiente registrada).

### Diff-scope review (bmad-review — 3 lentes sobre o diff do épico)

Achados re-verificados contra as fontes primárias nesta retro; convergência de lentes anotada.

**DS1 — Dreno offline não invalida o roster (3 lentes convergem).** `use-offline-sync.ts` não toca no cache do TanStack Query; o único `invalidateQueries` do app é o caminho online do `scan.tsx:202`. Check-ins enfileirados sincronizam e a lista/contagem continuam velhas até remount > staleTime. O próprio spec E2E documenta a lacuna (`api/tests/e2e/boarding-offline-sync.e2e.spec.ts:14-22` afirma via API, não via DOM). Já constava no defer 3-4b; esta retro adicionou consumidor e a constatação de que nenhum teste cobre. **Fix now.**

**DS2 — `SETTLED_CODES` apaga rejeições reais como "sent" (2 lentes).** `offline-queue.ts:87-96` trata `TRIP_NOT_ACTIVE`, `DRIVER_NOT_ASSIGNED`, `TRIP_NOT_FOUND`, `STUDENT_NOT_FOUND` como desfecho terminal benigno (`markSent`). Para um item cuja key **nunca chegou ao servidor** (enfileirado offline), esses códigos significam "embarque rejeitado", não "registrado" — o aluno some da contagem sem `failedCount`. O teste fixa o comportamento como correto (`offline-queue.test.ts:188-189`). A defesa do design (replay 201 cobre o caso "aceito antes de encerrar") só vale para itens já entregues. **Decisão de produto + fix.**

**DS3 — Fila sem identidade + logout não limpa (3 lentes).** `QueuedCheckIn` não tem `userId`; `auth.store.ts:49-56` limpa tokens/user/sessão/cache de query mas não a fila. Motorista B drena itens do motorista A com token de B num aparelho compartilhado → 403 → (com DS2) silenciosamente descartado como `sent`. Já deferido na 3-4b (mudança de schema, "Ask First"). **Decisão de produto; cresceu de gravidade com DS2.**

**DS4 — Mock MSW diverge do use case na ordem replay × occurredAt.** `boarding.handlers.ts:155` valida a janela de `occurredAt` **antes** do lookup de replay (`:171`); o use case real faz replay **antes** da sanidade de `occurredAt` (decisão da review 3.3a). Replay drenado >24h depois: API real 201, mock 400 `INVALID_QR_CODE`. Mesma classe do desvio mock×API corrigido na review da 3.3a. **Fix now (reordenação de 1 bloco no mock).**

**DS5 — 200 não-JSON (portal cativo) vira check-in "enviado" (edge-case; verificado).** `parseResponseJson` (`api-client.ts:65-72`) retorna `{}` em corpo não-JSON; `isTransportFailure` não captura; `send` resolve `undefined` → `accepted` → `markSent`. Servidor nunca registrou. Viola a própria fronteira do módulo ("nenhum item some em silêncio"). **Fix now (validar envelope antes de markSent).**

**DS6 — Split de disclosure 404×403 no mesmo domínio (verificado).** `end-trip.use-case.ts:32` responde `TripNotFound` (404, não-disclosure — decisão da review 3.1) para viagem de outro motorista; `get-trip-students.use-case.ts:41` responde `DriverNotAssigned` (403) para a mesma condição — oráculo de enumeração de trip ids. **Fix now (alinhamento barato) ou decisão registrada.**

**DS7 — `['activeTrip']` sem `networkMode: 'always'` (2 lentes; verificado).** Instância restante do defer sistêmico do `onlineManager`: cold start offline deixa a query pausada — `scan.tsx` (sem `networkMode`; grep limpo) gira "Carregando viagem..." indefinidamente; `trip.tsx` (que usa `isLoading`, que mente quando a query está pausada — `:161,262`) cai no ramo "sem viagem" e oferece "Iniciar Viagem" que só pode falhar. As telas irmãs foram corrigidas na 3.5b; `activeTrip` ficou de fora. **Fix now (por query, como na 3.5b) até o fix sistêmico do onlineManager.**

**DS8 — Retry assimétrico na mesma entrada de cache (verificado).** `student-list.tsx:58` pinha `retry` custom (não retenta 4xx); `trip.tsx` (studentsSummary) não — 403/404 na tela da viagem queima a escada default de retries antes de renderizar a contagem. **Fix now (extrair `queryOptions` compartilhado — elimina também o literal de query key repetido).**

**DS9 — Invariante "retry reenvia a MESMA idempotency key" sem teste (verification-gap).** Nenhum spec mobile renderiza `ScanScreen`; nenhum spec Playwright pressiona "Tentar novamente" ou inspeciona o header. Um refactor que minta key nova por submit regressa em silêncio (409 `DUPLICATE_CHECK_IN` após timeout com resposta perdida — exatamente o cenário que a reutilização da key existe para evitar). **Action item de teste.**

**DS10 — SQL da fila e hook de dreno sem teste que rode por padrão (verification-gap; já deferido na 3-4b, confirmado com consumidores).** `sqliteQueueStorage` e `use-offline-sync` não são importados por nenhum teste jest; o spec E2E auto-skipa sem os servidores. Remover `status='pending'` do WHERE de `listPending` reenviaria itens entregues com `npm test` verde. **Action item de teste (bateria compartilhada contra SQLite real).**

**DS11 — Bootstrap CORS sem teste e sem fail-fast (2 lentes; verificado).** `main.ts:21-37` cai para `localhost:8081` quando `CORS_ORIGIN` não está setada (warn apenas quando setada-e-inválida) e o comentário em código admite que o bootstrap nunca roda nos testes (que montam o AppModule direto). `AGENTS.md` declara CORS_ORIGIN obrigatória em produção — o código não força. **Fix now (fail-fast em produção) + teste de preflight.**

**DS12 — Linhas terminais da `offline_queue` nunca purgadas (adversarial; já deferido na 3-4b).** Crescimento ilimitado no device (`markSent`/`markFailed` só trocam status; teto de 500 conta só `pending`). **Defer (com proposal de TTL/pruning no boot).**
